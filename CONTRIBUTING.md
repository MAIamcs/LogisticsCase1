# Совместная разработка

Работаем через небольшие pull request в `main`. Перед изменениями прочитайте
[архитектуру](docs/architecture.md), [API](docs/api-contract.md),
[семантику прогноза](docs/forecast-contract.md) и инструкции проекта, если они
появились. Проверьте `git status`: чужие незавершённые изменения сохраняются.

## Локальный запуск

Нужны Node.js 22.12+ (CI использует 24), pnpm 11.25.0 и Python 3.11+
(CI использует 3.12). Из корня существующего checkout:

```sh
cd frontend
pnpm install --frozen-lockfile
cp .env.example .env.local
pnpm dev
```

По умолчанию работает `demo`, FastAPI не нужен. Vite печатает адрес локального
сервера. `predev` и `prebuild` копируют канонические ответы и геоданные в
игнорируемые `frontend/public/demo/` и `frontend/public/geography/`.
Эти копии не редактируются вручную.

Backend запускается отдельным процессом из корня репозитория:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r backend/requirements-dev.lock
python -m uvicorn app.main:app --app-dir backend --reload --host 127.0.0.1 --port 8000
```

Swagger: `http://127.0.0.1:8000/docs`. Для подключения frontend задайте в
`frontend/.env.local` `VITE_DATA_MODE=api` и
`VITE_API_BASE_URL=http://127.0.0.1:8000`, затем перезапустите Vite. Префикс
`/api/v1` к этой переменной не добавляется. Backend `.env.example` описывает
переменные; Uvicorn не загружает этот файл автоматически.

## Границы ответственности

| Направление | Что меняет и проверяет |
| --- | --- |
| Frontend | `frontend/`: доступность, адаптивность, карта, связанный выбор объекта, графики, состояния загрузки/ошибки, оба транспорта и пути ресурсов через Vite `BASE_URL`. Не рассчитывает критические интервалы или инженерные решения. |
| Backend | `backend/`: маршруты, Pydantic, параметры, ошибки, CORS, проверка согласованности ответов и провайдеров. Не размещается на GitHub Pages. |
| Аналитическая модель | Реализация `ForecastProvider`: базовый год из данных, годы, единицы, сценарии, стабильные ID, значения/null, агрегаты, качество, версии и обоснованные критические интервалы с рекомендациями. Не меняет API ради внутреннего формата модели. |
| Геоданные | `contracts/geography/`, `GeographyProvider` и импорт: исходные контуры, ID, привязка статистики, версия географии, полнота, атрибуция и условия каждого источника. |
| Интеграция | `contracts/`, документация и CI: совместимость схем, типов, fixtures, frontend и backend; согласованное развёртывание. |

Роли обозначают ответственность, а не назначенных людей. PR, затрагивающий
несколько границ, проверяют соответствующие участники команды.

## Как менять контракт

1. Опишите итоговый формат и совместимость в `docs/api-contract.md` и
   `docs/forecast-contract.md`; при изменении потока обновите архитектуру.
   Зафиксируйте единицы, nullable-поля, геометрию, версии и правила агрегирования.
2. Измените исходные Pydantic-модели/валидацию и маршруты FastAPI. OpenAPI
   FastAPI — источник API-типов; сгенерированные файлы вручную не исправляются.
3. Обновите адаптеры провайдеров, потребителей и содержательные тесты. Если
   изменились демонстрационные данные, исправьте
   `contracts/forecast-demo-source.json` и выполните
   `python scripts/create_forecast_fixtures.py`. Геоданные меняйте по
   [процедуре импорта](docs/geodata.md), с обновлением источников и версии.
4. Перегенерируйте схемы и TypeScript:

   ```sh
   python scripts/export_contract.py
   cd frontend
   pnpm types:generate
   cd ..
   ```

5. Проверьте diff OpenAPI, JSON Schema, TypeScript и канонических ответов.
   Запустите проверки ниже. Static fixtures проходят те же экспортированные
   схемы, которые использует клиент; backend дополнительно проверяет их
   семантическую согласованность и совпадение API/demo.
6. Включите исходники, сгенерированные артефакты, fixtures, тесты и документацию
   в один PR. Обоснуйте изменение версии и миграцию. Несовместимые изменения
   требуют согласования frontend, backend и разработчика модели до выпуска;
   поддерживаемые старые маршруты не удаляются без плана миграции.

Пропуск не равен нулю, процент при нулевой базе равен `null`. Проценты загрузки
не суммируются. Критические интервалы приходят от провайдера. Реальная география
не превращает демонстрационные значения в результаты модели.

## Проверки перед PR

Из корня, с активной `.venv` и установленными frontend-зависимостями:

```sh
python scripts/export_contract.py --check
python scripts/create_forecast_fixtures.py --check
python scripts/import_geography.py --check
python -m pytest backend/tests -q
cd frontend
pnpm exec tsc -b
pnpm types:generate
pnpm test
VITE_DATA_MODE=demo VITE_BASE_PATH=/LogisticsCase1/ pnpm build
VITE_DATA_MODE=api VITE_API_BASE_URL=https://api.example.test VITE_BASE_PATH=/LogisticsCase1/ pnpm build
cd ..
git diff --exit-code -- contracts/api.generated.ts
git diff --check
```

Если типы изменены намеренно, сначала включите их в свой коммит: проверка diff
выявляет несогласованную повторную генерацию. `https://api.example.test` —
заглушка только для сборки, а не развёрнутый сервис. Для ручной проверки demo
последней соберите именно demo и запустите `pnpm preview` из `frontend/`.

Для UI проверьте desktop и узкий экран, клавиатуру, липкую панель, каждый год,
критические отметки, быстрые переключения, выбор объекта и перезагрузку страницы.
Карта, числа и графики должны показывать одну выборку. Проверьте отказ одного
фонового слоя и ошибку API: сообщения явные, подмены API на demo нет. Для
изменений интерфейса приложите снимки; для контракта — результаты обоих режимов.

## Ветки, PR и секреты

- Новые агентские ветки: `codex/<краткая-тема>`. Существующие командные ветки
  сохраняются. Перед началом обновите сведения об `origin/main` через `git fetch`.
- Не используйте force push, reset чужих изменений или удаление командной работы.
  Если `main` изменился, согласуйте/разрешите конфликты в своей ветке и повторите
  проверки. Не обходите защиту веток.
- PR описывает проблему, итоговое поведение, затронутые границы и проверки.
  Используйте шаблон; незапущенные проверки отмечайте явно. Не заявляйте
  публикацию по одному наличию workflow или успешной локальной сборке.
- `.env.local`, токены, ключи и учётные данные в Git не попадают. Коммитятся только
  безопасные `.env.example`. Все `VITE_*` доступны посетителям собранного сайта.
  Удаляйте секреты из логов, issue, скриншотов и описаний PR.

## GitHub Pages и отдельный API

Официальный workflow `.github/workflows/pages.yml` публикует только static
frontend после проверок. По умолчанию это `demo` с префиксом `/LogisticsCase1/`.
Сайт использует один маршрут, поэтому обновление корневой страницы по этому
префиксу не требует SPA-rewrite. Пути JSON/GeoJSON должны использовать Vite
`BASE_URL`, а не абсолютный `/geography/...`.

Для `api` нужен отдельно развёрнутый HTTPS backend. Задайте build-переменные
`VITE_DATA_MODE=api`, `VITE_API_BASE_URL=https://<ваш-backend>` и
`VITE_BASE_PATH=/LogisticsCase1/`. В CORS backend разрешите точный origin
`https://maiamcs.github.io` без `/LogisticsCase1/`; credentials по умолчанию
выключены. `*` с credentials не используется. После изменения build-переменных
frontend пересобирается. Подробности и проверка фактической публикации — в
[руководстве разработки](docs/development.md).

Крупные `contracts/geography/roads.geojson` и `buildings.geojson` генерируются
из версионированного `source/osm-context.json.gz` и не хранятся повторно в Git.
Подготовка: `python3 scripts/import_geography.py` из корня. Frontend-команды
`pnpm dev`, `pnpm test` и `pnpm build` восстанавливают отсутствующие слои
автоматически; для этого нужен Python 3.11+. Содержимое GeoJSON и контрольные
суммы сохраняются без изменения.
